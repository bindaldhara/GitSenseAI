GitSense AI — Interview Answers
================================
Source questions: docs/learnings.md

----------------------------------------------------------------------------
FRONTEND
----------------------------------------------------------------------------

Q1. Why use React Router instead of keeping everything in one App.tsx component?
A1. A single App.tsx mixes landing content with repository management and does not
    scale. React Router gives clear URLs (/ and /repositories), shared layout via
    Outlet, and independent page components. That matches a product that will grow
    into chat, dashboards, and multi-session flows without rewriting one giant file.

Q2. What is the difference between BrowserRouter, Routes, Route, Outlet, and NavLink?
A2. BrowserRouter enables HTML5 history-based client routing.
    Routes is the route table container.
    Route maps a path to a page element.
    Outlet is the placeholder where nested child routes render (used in AppLayout).
    NavLink is a Link that can style itself when the current path is active.

Q3. How does React Query’s useMutation + invalidateQueries keep the repositories
    list fresh after submit?
A3. useMutation runs POST /api/v1/repositories. On success, invalidateQueries with
    key ['repositories'] marks the list query stale. React Query refetches GET
    /api/v1/repositories, so the UI shows the new row without manual setState list
    merging. Reindex and delete mutations invalidate the same key.

Q4. When would you prefer React Query over local useState for API data?
A4. Prefer React Query for server state: caching, retries, loading/error flags,
    background refetch, and shared cache across components. useState is better for
    pure UI state (form input text, which modal is open) that does not come from an API.

Q5. Why keep API calls in src/api/ with a shared Axios client instead of calling
    HTTP inside every page?
A5. Centralizing Axios in src/lib/axios.ts keeps base URL, headers, and error parsing
    in one place. API modules (repositories.ts, health.ts) expose typed functions.
    Pages stay focused on UI. When endpoints change, you update one module instead
    of hunting through components.

Q6. What problem does Vite’s proxy solve in local development?
A6. The browser may call same-origin /api paths while Vite forwards them to
    localhost:8000. That reduces CORS friction during local frontend development
    when the API runs on another port. (This project also supports VITE_API_URL for
    direct calls to the backend.)

Q7. Why render the parse summary modal with createPortal to document.body?
A7. Modals need to overlay the whole viewport and sit above the header. Rendering
    inside the page tree can trap position:fixed elements inside animated/transformed
    parents, which makes the modal appear too low. createPortal mounts the modal at
    document.body so it centers correctly regardless of page scroll or layout.

Q8. Why avoid transform animations on a parent wrapper when using position: fixed
    modals?
A8. CSS transform on an ancestor creates a new containing block for fixed children.
    A modal marked fixed then positions relative to that ancestor, not the viewport.
    That is why AppLayout uses a fade-only page-enter animation instead of translateY
    on the route wrapper.

Q9. How would you add a third route (for example Chat) without rewriting the layout?
A9. Keep AppLayout with the header/nav and Outlet. Add a ChatPage component and a
    new Route path="/chat" under the same layout Route. Add a NavLink to Chat in
    the header. Home and Repositories stay untouched.

Q10. What happens in Docker if you add a new npm package but the frontend container
     keeps an old anonymous node_modules volume?
A10. Compose mounts host source into /app but keeps /app/node_modules in a Docker
     volume. Old volumes lack new packages, so Vite fails to resolve imports even
     though package.json lists them. Fix by rebuilding and removing the stale volume,
     or running npm install inside the container / on container start.

Q11. How would Socket.io later complement React Query for streaming chat?
A11. React Query fits request/response and cached resources (repo list, health, parse
     summary). Socket.io fits push streams: token-by-token chat, indexing progress,
     live status. Typical pattern: React Query for snapshot data; Socket.io for live
     event streams that update UI as events arrive.

----------------------------------------------------------------------------
BACKEND
----------------------------------------------------------------------------

Q1. Why separate route handlers (repositories.py) from business logic
    (repository_service.py and parsers/service.py)?
A1. Routes handle HTTP concerns (status codes, query params, response models). The
    repository service owns clone/delete/reindex and status updates. The parser
    service owns walking files, extracting symbols, and persisting parse tables.
    That keeps handlers thin and makes logic reusable for workers/MCP later.

Q2. What does FastAPI’s lifespan do, and why initialize the DB there?
A2. Lifespan runs startup code before serving and optional shutdown after.
    initialize_database() ensures repositories and parse tables exist once at boot so
    every request does not recreate schema. It is the right place for one-time wiring.

Q3. How does APIRouter prefix stacking produce
    /api/v1/repositories/{id}/parse-summary?
A3. repositories.router has prefix="/repositories". main.py includes it with
    prefix=settings.api_v1_prefix ("/api/v1"). A route like
    "/{repository_id}/parse-summary" becomes /api/v1/repositories/{id}/parse-summary.

Q4. Why make POSTGRES_* required in Settings instead of hardcoding defaults?
A4. Required env vars fail fast if .env is missing or wrong. That prevents
    accidentally connecting to the wrong host (for example silent default localhost
    while Docker expects postgres). Secrets and environment-specific hosts should not
    live as code defaults.

Q5. Explain @computed_field vs a plain @property in Pydantic Settings.
A5. @property makes a derived Python attribute (database_url from parts).
    @computed_field also registers it with Pydantic so it participates in the model’s
    schema/serialization as a first-class field, not only as a plain Python property.

Q6. Why clone with git clone --depth 1 instead of a full clone for the MVP?
A6. Depth 1 is a shallow clone of the latest commit. It is faster and uses less
    disk/network, which is enough to get the tree on disk for parsing. Full history
    can come later if blame/history analysis needs it.

Q7. Why mark status cloning → parsing → cloned/failed?
A7. cloning records that git is running. parsing records that tree-sitter indexing
    is running after a successful clone. cloned/failed is the durable final outcome.
    The dashboard can show progress and debug stuck states instead of one opaque step.

Q8. What HTTP status codes fit: invalid URL, duplicate repo, missing git binary,
    clone failure, parse failure?
A8. Invalid GitHub URL → 422 Unprocessable Entity.
    Duplicate submission → 409 Conflict.
    Missing git binary → 500 Internal Server Error (server misconfigured).
    git clone failure → 502 Bad Gateway (upstream/git failed).
    Parse failure after clone → 500 Internal Server Error (indexing failed).

Q9. Why is synchronous clone + parse acceptable for the MVP but risky for large
    repos later?
A9. The MVP keeps the flow simple: one request does validate → DB → clone → parse →
    response. Large repos can block the worker for minutes and hit timeouts. Later,
    enqueue Celery jobs and return quickly with status polling or websockets.

Q10. How would Celery change the submit-repository flow?
A10. POST would create a row (status=queued/cloning) and enqueue clone+parse tasks,
     then return 202/201 immediately. A worker runs git clone and parsing, updating
     status through cloning/parsing/cloned/failed. The UI polls GET /repositories or
     uses websockets instead of waiting on one long HTTP request.

Q11. Why use tree-sitter instead of language-specific AST libraries?
A11. tree-sitter gives one query-based API across Go, Python, JS, and TS with good
     performance and incremental parsing potential. It avoids mixing ast (Python),
     babel (JS), and go/parser with different object models. For symbol extraction
     in an MVP, tree-sitter is consistent and easy to extend.

Q12. What is a “symbol” in GitSense, and what gets stored in repository_symbols?
A12. A symbol is a named meaningful code unit: function, class, method, type, or
     import. Each row stores name, kind, start/end line, optional signature and
     parent_name, plus foreign keys to repository and file. This is the index Day 5
     chunking/embeddings can build on.

Q13. Why record skipped files separately instead of only counting them?
A13. Skipped paths explain why a repo looks under-parsed (unsupported_language,
     binary, oversized, parse_error). Counts alone cannot tell whether .md files or
     broken files caused gaps. repository_skipped_files powers the parse summary UI
     and future diagnostics.

Q14. How does reindex clear stale parse data before re-cloning?
A14. reindex_repository calls cleanup hooks, clear_parsed_data (symbols/files/
     skipped rows), removes the clone directory, re-clones, then parse_repository
     replaces all parse tables for that repo. That prevents stale symbols from an
     old tree surviving after a fresh clone.

----------------------------------------------------------------------------
DATA AND INFRASTRUCTURE
----------------------------------------------------------------------------

Q1. Why store repository metadata in PostgreSQL and the code itself on disk?
A1. Postgres is good for structured records: id, url, status, symbols, timestamps,
    query/filter. Source trees are large file trees better kept on disk for git and
    parsers. Metadata and parse artifacts in DB, content on disk is a common split.

Q2. Why should cloned repos under data/repos/ be gitignored?
A2. Each clone is its own git repo. Committing them creates embedded-repo warnings,
    huge diffs, and broken clones for other developers. Clones are regenerable via
    submit/reindex; only metadata belongs in the project repo.

Q3. What is the difference between POSTGRES_HOST=postgres and
    POSTGRES_HOST=localhost?
A3. postgres is the Compose service DNS name — works only inside the Docker network
    (backend container → postgres container). localhost is the host machine loopback
    — used by Mac apps (Postico) and a backend started with make backend against
    Homebrew or published Docker ports.

Q4. Why can Postico fail with “hostname not found” when host is set to postgres?
A4. Postico runs on the Mac, outside Docker’s network. The name postgres is not
    resolvable on the Mac. Use localhost and the published port 5432 instead.

Q5. What is the difference between a Dockerfile and Docker Compose?
A5. A Dockerfile builds one image (how to package frontend or backend). Compose
    defines and runs a multi-service stack (frontend, backend, postgres, redis,
    qdrant), networking, ports, volumes, and env files together.

Q6. Why run Redis and Qdrant in Compose before the app reads from them?
A6. Day 2 provisions infra early so Day 5+ work does not fight setup later.
    Services can be healthy and reachable while app code still only uses Postgres.
    This matches incremental Week 1 delivery.

Q7. What is an anonymous Docker volume, and how did it break react-router-dom
    until rebuilt?
A7. Compose uses /app/node_modules as an anonymous volume so host mounts do not
    wipe container dependencies. That volume kept an older install without new
    packages after package.json changed. Rebuild + remove stale volume (or npm install
    in container) fixed it.

Q8. Why install git in the backend image?
A8. Cloning uses subprocess git. python:3.12-slim does not include git by default.
    Without git, clone fails and can leave status stuck at cloning. Installing git in
    the Dockerfile makes the container able to clone.

Q9. How do repository_files, repository_symbols, and repository_skipped_files
    relate?
A9. repository_files is one row per parsed source file (path, language, size).
    repository_symbols references file_id and stores extracted symbols. repository_
    skipped_files stores paths that were scanned but not parsed, with a reason.
    All cascade-delete when a repository is removed.

Q10. What data belongs in Postgres vs Qdrant vs Redis in the full GitSense design?
A10. Postgres: users, repos, parse tables, chat sessions/history, job status.
     Qdrant: vector embeddings and payloads for semantic retrieval.
     Redis: semantic/response cache, rate limits, Celery broker/results, short-lived
     session or progress keys.

----------------------------------------------------------------------------
PRACTICE PROMPTS (MODEL ANSWERS)
----------------------------------------------------------------------------

P1. Explain the current GitSense AI architecture in 2 minutes (through Day 4).
A.  GitSense is a full-stack MVP: React/Vite/Tailwind UI with React Router pages
    for Home and Repositories, talking to a FastAPI backend over Axios + React Query.
    Backend persists repository metadata and parse results in PostgreSQL, clones
    public GitHub repos with git, and parses Go/Python/JS/TS with tree-sitter into
    files/symbols/skipped-file tables. Docker Compose can run frontend, backend,
    Postgres, Redis, and Qdrant; Redis/Qdrant are provisioned but not used by app
    logic yet. Day 4 ends at clone + parse + dashboard summary modal; embeddings and
    chat are later.

P2. Walk through what happens when a user submits https://github.com/owner/repo.
A.  Frontend POSTs JSON {url} to /api/v1/repositories. FastAPI validates the body,
    service parses/normalizes the GitHub URL, rejects non-GitHub or duplicates,
    inserts status=cloning, runs git clone --depth 1, sets status=parsing, walks the
    clone with tree-sitter, persists repository_files/symbols/skipped_files, then
    sets status=cloned (or failed). React Query invalidates the list query.

P3. Walk through what happens when a user clicks View parse summary.
A.  RepositoriesPage opens ParseSummaryModal via createPortal. React Query fetches
    GET /api/v1/repositories/{id}/parse-summary?skipped_limit=100. Backend reads
    counts from repository_files, repository_symbols, and repository_skipped_files,
  returns by_language, by_kind, by_skip_reason, and a capped skipped-file list.
    The modal shows stats and a scrollable skipped-files section.

P4. Why are React Query and FastAPI a strong pair for this MVP?
A.  FastAPI gives typed request/response models and clear REST endpoints. React
    Query consumes those endpoints with caching, mutations, and loading/error UX.
    Together they keep HTTP concerns explicit and UI state for server data clean,
    which is ideal while the product is still endpoint-driven before streaming.

P5. Compare local Homebrew Postgres vs Docker Compose Postgres for development.
A.  Homebrew: Postgres on the Mac, POSTGRES_HOST=localhost, no Docker daemon needed
    for DB, good for make backend. Compose: Postgres in a container named postgres,
    POSTGRES_HOST=postgres for the backend container, same published localhost:5432
    for Mac UIs. Compose matches production-like multi-service setups; Homebrew is
    lighter when Docker is unavailable.

P6. How would you move cloning/parsing from request/response to a background worker
    without breaking the UI?
A.  Change POST to create a queued row and enqueue Celery tasks for clone then parse;
    return quickly. Keep GET /repositories for status and GET /parse-summary once
    cloned. UI already shows status badges and can poll until cloned/failed. Same
    API contract for listing and summary; only submit timing changes.

P7. Describe how you would add authentication and multi-user repository ownership
    later.
A.  Add JWT auth (Week 2 plan): users table, login/register, protect repository
    routes. Add user_id (or org_id) on repositories and filter list/create by owner.
    Frontend stores token and sends Authorization header via the Axios client.

P8. Design the next steps: chunking → embeddings → chat retrieval using today’s
    symbol index.
A.  Day 5: chunk source around symbols or file sections, embed with sentence-
    transformers or an API, upsert into Qdrant with repo/file/symbol metadata.
    Day 6: chat API retrieves relevant chunks (later hybrid with BM25), generates
    answers with citations. Day 7: chat UI. Today’s repository_symbols table gives
    structured anchors so chunking is smarter than raw file splits.
